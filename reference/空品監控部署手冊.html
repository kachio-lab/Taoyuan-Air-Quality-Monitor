01

架構總覽

整條管線其實是兩個各自獨立、循環週期不同的自動化流程。

每小時流程負責「線上」的部分：抓最新一小時的觀測值、 用已經訓練好的模型做預測、等實際值進來後自動評分、更新儀表板。 

flowchart LR
    MOENV["環境部\naqx_p_432"] --> FETCH["fetch.py"]
    CWA["中央氣象署\nO-A0001-001"] --> FETCH
    FETCH --> OBS[("observations.csv")]
    MODELS[("models/*.joblib")] --> PRED["predict.py"]
    OBS --> PRED
    PRED --> PREDCSV[("predictions.csv")]
    OBS --> EVAL["evaluate.py"]
    PREDCSV --> EVAL
    EVAL --> SCORES[("scores.csv\nmetrics.json")]
    SCORES --> DASH["dashboard.py"]
    DASH --> PAGE["docs/index.html"]
    SCORES -.-> NOTIFY["notify.py（選用）"]

每小時流程（run_hourly.py，由 hourly-monitor.yml 觸發）

每月流程負責「離線」的部分：用累積下來的觀測資料重新訓練模型、 跑一次歷史回測，確認新模型沒有變差。 

flowchart LR
    HIST[("history.csv\n2025+2026 歷史資料")] --> TRAIN["train.py"]
    OBS2[("observations.csv\n累積的即時觀測")] --> TRAIN
    TRAIN --> MODEL2[("models/pm25_桃園_h1.joblib\nmodels/pm25_桃園_h3.joblib")]
    MODEL2 --> BT["backtest.py"]
    BT --> BTJSON[("docs/backtest.json")]

每月流程（monthly-retrain.yml 觸發，預設每月 1 日）

兩條流程共用同一份 pipeline/settings.py 與 pipeline/features.py，所以訓練時用什麼特徵、線上預測時就用什麼特徵， 不會出現「訓練和上線兜不起來」的落差。

檔案地圖

檔案角色
pipeline/settings.py測站、API、路徑、警示門檻、AQI 分級表
pipeline/build_history.py整併歷史 CSV → history.csv（只需跑一次）
pipeline/features.py特徵工程，訓練與推論共用同一份程式碼
pipeline/train.py比較演算法、交叉驗證、存模型
pipeline/backtest.py保留期回測，給上線前的成效基準
pipeline/fetch.py抓即時觀測（AQI ＋ 氣象）
pipeline/predict.py用最新觀測產生 +1h／+3h 預測
pipeline/evaluate.py預測對上實際值，算成效
pipeline/dashboard.py產生 docs/index.html
run_hourly.py每小時排程的進入點
02

資料從哪裡來

兩種格式、三種來源，最後全部收斂成同一張長表。

build_history.py 只需要執行一次， 它會掃描專案根目錄底下幾個地方，把找到的歷史資料整併成 data/monitor/history.csv：

  • 環境部原始寬表——像 北部空品區_2025 (1)/桃園_2025.csv 這種「一列一個測項、00~23 橫向排列」的格式，會先 melt 成長表再 pivot 回「一列一個時間戳記」。
  • 課堂整理過的長表——像 2026_01_07桃園五站空品監測資料_精簡20欄合體版.csv， 欄位已經是一列一筆觀測，直接讀取、對齊欄名即可。
  • 環境部即時 API——上線後由 fetch.py 每小時累加寫入 observations.csv，訓練時會和 history.csv 合併使用。

同測站同一整點如果被抓到兩次（例如寬表和長表都有），會保留非空欄位比較多的那一筆， 避免用一筆到處都是缺值的紀錄蓋掉一筆完整的紀錄。

terminal
# 只需要執行一次，之後由 fetch.py 每小時累積新資料
python -m pipeline.build_history

輸出的標準欄位（SCHEMA_COLUMNS）固定是：

pipeline/settings.py
sitename, publishtime,
pm2.5, pm10, o3, co, so2, no, no2, nox,
wind_speed, wind_direc, amb_temp, rh

其中 amb_temp（氣溫）與 rh（濕度）不在環境部即時 API 裡，是 fetch.py 另外呼叫中央氣象署 API、依經緯度配對最近的有效氣象站補上的。 這一步失敗只會警告、不會中斷整條流程——氣象是輔助欄位，AQI 資料才是主角。

03

特徵工程

同一份 features.py，訓練和上線推論都呼叫它——不會有兩套邏輯兜不起來的風險。

做特徵之前，to_hourly_grid() 會先把時間軸補成連續的整點格點。 這一步很關鍵：如果不補齊，某個測站缺了兩小時的資料時，shift(1) 拿到的就不是「一小時前」而是「更早以前最後一筆有資料的時刻」，滯後特徵的物理意義會整個跑掉。

衍生出的科學指標

公式沿用課堂 EDA notebook 的既有定義：

欄位公式用途
oxo3 + no2總氧化劑，光化學反應強度
pm_ratiopm2.5 / pm10細懸浮微粒佔比，判斷污染來源
co_nox_ratioco / nox交通排放特徵比值
sat_vapor_pressMagnus 公式（氣溫）飽和水蒸氣壓
wind_x / wind_y風速 × cos／sin(風向)把風向拆成向量，0° 和 359° 不再是天差地遠
hour_sin / hour_cos週期編碼讓模型知道 23 點和 0 點是相鄰的

滯後與滾動特徵

這才是預測準度的主力：pm2.5 和 ox 各取 1, 2, 3, 6, 12, 24 小時前的值，再加上 3 小時 / 24 小時的滾動平均與標準差， 以及 1 小時 / 3 小時的差分。

i

最長的滯後是 24 小時，這代表模型要「暖機」滿 25 小時的連續觀測， 最新一筆的滯後特徵才會是完整的。上線的頭一天，預測會標記 warmup=True， 儀表板會顯示暖機橫幅，而且這段期間的預測不列入成效統計—— 放進去只會讓數字虛胖，沒有意義。

怎麼避免用到「未來」的資料

預測 t+h 小時後的 PM2.5 時，t 時刻的觀測值是「已經拿得到的資訊」，所以特別留了一欄 pm2.5_now 當合法特徵； 但原始的 pm2.5 欄位（也就是目標欄位本身）會被明確排除在特徵矩陣外， 滾動與差分也全部只往過去看（rolling()、diff(正數)）。 目標值本身用 shift(-horizon) 產生，訓練與驗證之間另外留了 24 小時空隙（TimeSeriesSplit(gap=24)）， 雙重防止資訊從未來洩漏回訓練集。

04

訓練與回測

四種演算法賽馬，時間序列交叉驗證挑最佳者，再用完全沒看過的資料驗一次。

train.py 針對每個預測時距（+1h、+3h）各自訓練， 每個候選模型都是 補值 → Min-Max 正規化 → 迴歸器 的 pipeline，就算即時資料臨時缺一兩個欄位也不會整條掛掉。

terminal
# 訓練 +1h 與 +3h 兩個模型（約 1~2 分鐘）
python -m pipeline.train

# 用最後 45 天做保留期回測
python -m pipeline.backtest --holdout-days 45

候選演算法

RandomForest、HistGradientBoosting、Ridge，加上有裝才會參戰的 LightGBM。 用 TimeSeriesSplit(n_splits=5, gap=24) 各跑 5 摺交叉驗證， RMSE 差距在 1% 以內視為平手，平手時優先選模型檔比較小的—— 模型要 commit 進 repo，體積會隨每月重訓累積。

回測成效（實測基準）

用 2026-06-16 ~ 07-31（45 天）完全沒參與訓練的資料驗證：

時距MAERMSER²勝過 persistence誤差 ≤5 佔比
+1 小時2.252.880.58+7.9%92.0%
+3 小時2.943.770.29+12.9%82.5%
?

「勝過 persistence」是什麼？ persistence 基準線＝「假設下一小時濃度和現在一樣」。PM2.5 本來就有很強的時間自相關， 這個笨方法的 MAE 通常就已經不差了。模型如果贏不過它，代表沒有真正的預測能力—— 所以這一欄比單看 MAE 本身更重要，正值才算及格。

05

每小時自動化流程

run_hourly.py 依序呼叫五個模組，這是 GitHub Actions 每小時實際執行的內容。

  1. fetch — 呼叫環境部 API 拿最新一小時的 5 站觀測，補氣象欄位，累加寫入 observations.csv（同測站同時間戳記只留最新一筆）。
  2. predict — 讀最近 72 小時觀測、算特徵，用存好的模型預測 +1h／+3h，寫入 predictions.csv。
  3. evaluate — 把之前產生、目標時間已經到了的預測，對上這次抓到的實際值， 算 MAE / RMSE / R² / bias，並和 persistence 基準比較，輸出 docs/metrics.json。
  4. dashboard — 用 metrics.json 重新產生 docs/index.html， 純 inline SVG 畫圖，零外部相依，離線也打得開。
  5. notify（選用）— 沒設定 LINE 金鑰就直接跳過；有設定的話，實測或預測超過門檻 （預設 35.5 µg/m³，對應「對敏感族群不健康」等級）才會推播，不會每小時洗版。
!

任一關鍵步驟（fetch／predict／evaluate／dashboard）失敗， run_hourly.py 會印出完整錯誤並回傳非零狀態碼， 讓 GitHub Actions 把那次執行標記成失敗，方便你在 Actions 頁面一眼看到。 但 notify 失敗只會警告，不影響資料與儀表板。

06

上架到 GitHub

從本機推上去，到排程真的開始跑，一共四步。

  1. 01

    本機先跑過一輪，確認金鑰沒問題

    訓練與回測都要在本機先做一次——GitHub Actions 只負責「每小時抓資料＋預測」， 不負責從零訓練模型，模型檔是直接被 commit 進 repo 帶上去的。

    terminal
    pip install -r requirements.txt
cp .env.example .env          # 填入 MOENV_API_KEY 與 CWA_API_KEY
python -m pipeline.build_history
python -m pipeline.train
python -m pipeline.backtest
python run_hourly.py          # 實跑一次，確認 API 金鑰沒問題
  2. 02

    推上 GitHub

    .env 已經在 .gitignore 裡，金鑰不會被推上去。 data/monitor/、models/、 docs/ 則是刻意要進版控的—— 之後 Actions 每小時會把新資料 commit 回這個 repo，等於拿 git 當資料庫。

    terminal
    git init
git add .
git commit -m "feat: 桃園測站 PM2.5 即時監控自動化"
git branch -M main
git remote add origin https://github.com/<帳號>/<repo>.git
git push -u origin main
  3. 03

    設定 repository secrets

    Settings → Secrets and variables → Actions → New repository secret， 名稱要和 pipeline/settings.py 讀取的環境變數完全一致：

    Secret 名稱必要性說明
    MOENV_API_KEY必要環境部開放資料平台金鑰
    CWA_API_KEY建議沒有的話氣溫/濕度缺值，模型仍能跑，準度較差
    LINE_CHANNEL_ACCESS_TOKEN選用要 LINE 推播才需要
    LINE_USER_ID選用同上
  4. 04

    開啟 GitHub Pages，驗證排程

    Settings → Pages → Source 選 Deploy from a branch，Branch 選 main + /docs，按 Save。一兩分鐘後儀表板就會在 https://<帳號>.github.io/<repo>/ 上線。

    接著到 Actions 分頁找到「每小時空品監控」， 按 Run workflow 手動觸發一次，確認能跑成功、 而且真的把新資料 commit 回 repo（工作流程結尾有 git push）。

07

儀表板怎麼看

docs/index.html 由 dashboard.py 每小時重新產生，幾個欄位值得多看一眼。

  • 偏差（bias）——正值代表系統性高估、負值代表低估。長期偏向同一邊， 就是重訓的訊號。
  • 勝過基準——見上一節，這是判斷模型有沒有用的第一指標。
  • 等級命中率——預測與實際落在同一個 PM2.5 空品等級 （良好／普通／對敏感族群不健康…）的比例。對「要不要發警示」這個決策， 比單看 MAE 更貼近實際用途。

成效分成兩種並列顯示：歷史回測成效是上線前就算得出來的（見上一節）； 即時監控成效是上線後累積的真實表現，會隨時間越來越有代表性， 拆成近 24 小時／7 天／30 天／全部四個統計窗格。

原始資料都留著沒有藏起來：data/monitor/scores.csv 是逐筆的預測與實際值對照，可以直接拉進 Excel 或 Python 自己分析。

08

常見問題與限制

上線前該知道的幾件事，省得半夜被 Actions 失敗通知嚇醒。

!

建模 notebook 裡有寫死的 LINE token，推上 GitHub 前務必先處理。

桃園空品分析建模(16個模型3個模式).ipynb 最後一個 cell 直接寫死了真實的 LINE Channel Access Token 與 User ID。 一旦推上去，這串字就永遠留在 git 歷史裡，事後刪掉 cell 也救不回來。 正確做法：先到 LINE Developers Console 撤銷、重發該 token， 再把 cell 改成讀環境變數（寫法可以直接參考 pipeline/notify.py）。

已知限制

  • 前 25 小時是暖機期，預測僅供參考、不列入成效統計（見第 3 節）。
  • GitHub Actions 的排程不保證準時，尖峰時段延遲 5~20 分鐘很常見， 偶爾會整點跳過——管線設計成「補得回來」，漏一小時只是少一筆觀測，不會壞掉。
  • repo 連續 60 天沒有 commit，GitHub 會自動停用排程。 本管線每小時都會 commit，正常運作下不會觸發；如果手動停用過再恢復， 記得回 Actions 頁面確認排程還活著。
  • 模型檔會進版控，每個約 1.9 MB。重訓設成每月一次而不是每週， 避免 repo 體積長太快；要更頻繁可以改 monthly-retrain.yml 的 cron。
  • 即時 API 只給當下一小時，歷史缺口補不回來。漏很多的話， 等環境部把該月資料上架後重跑 build_history 補進 history.csv。

換一個監控站

例如想改成監控平鎮站：

terminal
TARGET_STATION=平鎮 python -m pipeline.train
TARGET_STATION=平鎮 python run_hourly.py

Actions 上要換站，就在 workflow 的 env: 區塊加一行 TARGET_STATION: 平鎮。
